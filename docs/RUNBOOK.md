# Runbook — common operational tasks

This document is a working reference for the kinds of changes and
investigations you make against the v2 pipeline once it is up and
running. Each procedure is presented as a numbered checklist with the
exact commands and the expected output.

For *why* the pipeline looks the way it does, see
[`ARCHITECTURE.md`](ARCHITECTURE.md).

## Conventions

- All commands are run from the repository root with the virtual
  environment active:
  ```bash
  cd youtube-protest-semantic && source .venv/bin/activate
  ```
- `<...>` in commands indicates a placeholder you must substitute.
- Output excerpts are shown indented under each step.

## Add a new anchor query

Anchor queries live in `pipeline/stage_b_retrieve.py::ANCHORS`. Each
key is a short identifier; each value is a Russian-language
description of the political context.

1. Open `pipeline/stage_b_retrieve.py` and locate the `ANCHORS`
   dictionary.

2. Add a new key/value pair. Keep the description in Russian, list
   event names in their original spelling, and include three to six
   period-specific named entities (people, slogans, places).

   ```python
   ANCHORS = {
       # ... existing anchors ...
       "BY-2020-women-march":
           "женский марш в Беларуси осенью 2020 года, "
           "белые цветы, цепи солидарности, женщины в белом, "
           "Светлана Алексиевич, Минск, Гродно",
   }
   ```

3. Re-run Stage B for both encoders. The script does not depend on
   the previous outputs and is safe to re-run.

   ```bash
   python pipeline/stage_b_retrieve.py --table videos \
          --model intfloat/multilingual-e5-small \
          --out-dir outputs/retrieval

   python pipeline/stage_b_retrieve.py --table videos_e5large \
          --model intfloat/multilingual-e5-large \
          --out-dir outputs/retrieval_e5large
   ```

4. Re-run Stage D so the comparison summary picks up the new anchor.

   ```bash
   python pipeline/stage_d_ensemble.py
   ```

5. Inspect the new row in `outputs/retrieval_ensemble/comparison_summary.csv`.

> **Tip.** Anchor quality varies. Pilot a new anchor on the demo
> dataset first (see [Run end-to-end smoke test on demo
> data](#run-end-to-end-smoke-test-on-demo-data)) — top-10 inspection
> tells you within a minute whether the wording captures the intended
> concept.

## Swap the embedding model

The pipeline is parameterised by `--model` and `--table`. To try a
different multilingual encoder (e.g. `BAAI/bge-m3` or
`jinaai/jina-embeddings-v3`):

1. Embed the corpus with the new model into a fresh LanceDB table:

   ```bash
   python pipeline/stage_a_embed.py \
          --model BAAI/bge-m3 \
          --table videos_bge \
          --batch 8
   ```

   Adjust `--batch` if you run into thermal throttling on M2. See
   ADR-4 in `ARCHITECTURE.md`.

2. Run Stage B against the new table:

   ```bash
   python pipeline/stage_b_retrieve.py \
          --table videos_bge \
          --model BAAI/bge-m3 \
          --out-dir outputs/retrieval_bge
   ```

3. (Optional) Run Stage C polysemy clustering on the new embeddings:

   ```bash
   python pipeline/stage_c_polysemy.py \
          --table videos_bge \
          --out-dir outputs/polysemy_bge
   ```

4. Compare top-K overlap with the existing encoders to decide whether
   to integrate the new model into Stage D. A quick script:

   ```python
   import pandas as pd
   old = pd.read_csv("outputs/retrieval/topk_per_anchor.csv")
   new = pd.read_csv("outputs/retrieval_bge/topk_per_anchor.csv")
   for a in sorted(old["anchor"].unique()):
       s = set(old[old["anchor"]==a]["YT_ID"])
       n = set(new[new["anchor"]==a]["YT_ID"])
       print(f"{a:25s}  overlap={len(s&n):3d}/100")
   ```

> **Caution.** Different encoders have different input conventions.
> e5 needs `"passage: "` / `"query: "` prefixes; bge does not. The
> prefix is added in `pipeline/stage_a_embed.py::load_feed` and in
> `stage_b_retrieve.py` where queries are encoded. Adjust both
> together when changing model family.

## Rebuild the demo dataset

The demo dataset in `data/demo/` is generated by a single script.
Re-running it is safe and deterministic (seed=42).

1. Make sure the source LanceDB exists at `outputs/v2_lancedb` with
   both `videos` and `videos_e5large` tables.

2. Run the build script:

   ```bash
   python scripts/build_demo_dataset.py
   ```

   Expected output:
   ```
   [1/4] Reading metadata from outputs/v2_lancedb/videos
         21,710 videos in source table
   [2/4] Stratified sample of 200 videos (seed=42)
     R         protest+=25  protest-=25
     UR        protest+=22  protest-=23
     ...
         200 YT_IDs written to data/demo/yt_ids.txt
   [3/4] Building demo LanceDB at data/demo/lancedb
     wrote table 'videos_demo' (200 rows, 99 with protest keyword)
     wrote table 'videos_demo_large' (200 rows, 99 with protest keyword)
   [4/4] On-disk size
         1.14 MB
   ```

3. (If shipping a new release) verify the demo still runs end-to-end:
   see [Run end-to-end smoke test on demo
   data](#run-end-to-end-smoke-test-on-demo-data).

> **Why this is needed.** When the source corpus changes (e.g. after
> extending coverage), the demo should be rebuilt so that it remains
> a faithful slice. The seed makes the YT_ID list deterministic *up
> to* the source table contents.

## Run end-to-end smoke test on demo data

Use this whenever you want a fast confidence check that nothing is
broken — typically after a code change, a dependency update, or a
fresh `git clone`.

1. Stage B against demo (both encoders):

   ```bash
   python pipeline/stage_b_retrieve.py \
          --lancedb data/demo/lancedb --table videos_demo \
          --model intfloat/multilingual-e5-small \
          --top-k 30 --out-dir outputs/demo_retrieval

   python pipeline/stage_b_retrieve.py \
          --lancedb data/demo/lancedb --table videos_demo_large \
          --model intfloat/multilingual-e5-large \
          --top-k 30 --out-dir outputs/demo_retrieval_large
   ```

2. Stage C (k=4 instead of k=8 for the smaller sample):

   ```bash
   python pipeline/stage_c_polysemy.py \
          --lancedb data/demo/lancedb --table videos_demo \
          --n-clusters 4 --out-dir outputs/demo_polysemy
   ```

3. Stage D:

   ```bash
   python pipeline/stage_d_ensemble.py \
          --small-csv outputs/demo_retrieval/topk_per_anchor.csv \
          --large-csv outputs/demo_retrieval_large/topk_per_anchor.csv \
          --top-k 30 --out-dir outputs/demo_ensemble
   ```

4. Expected total runtime on first run: about 30 seconds (dominated
   by the one-time download of encoder weights from Hugging Face).
   Subsequent runs: ~5 seconds.

5. To clean up:

   ```bash
   rm -rf outputs/demo_*
   ```

> **What this verifies.** The schema of the demo tables matches what
> the pipeline expects; the cosine metric is being applied; the
> fusion functions produce sensibly ranked output. The exact numbers
> are *not* meaningful — 200 videos is too small a sample for the
> recall-gain claims to hold.

## Investigate why a video ranked where it did

Sometimes you want to know: *why is this specific video at rank 7
for anchor X?* Useful for sanity-checking the encoder.

1. Identify the YT_ID and the anchor.

2. Compute the cosine similarity between the anchor query vector
   and the video's stored vector. The cleanest way is interactively:

   ```python
   import lancedb, numpy as np
   from sentence_transformers import SentenceTransformer

   db = lancedb.connect("outputs/v2_lancedb")
   tbl = db.open_table("videos_e5large")
   row = tbl.search().where("YT_ID = '<YT_ID>'").limit(1).to_pandas().iloc[0]
   v = np.array(row["vector"], dtype=np.float32)

   model = SentenceTransformer("intfloat/multilingual-e5-large", device="mps")
   model.half()
   anchor_text = "<paste the anchor text from ANCHORS>"
   q = model.encode(["query: " + anchor_text],
                    normalize_embeddings=True,
                    convert_to_numpy=True).astype(np.float16)[0]
   cos = float(np.dot(q, v))
   print(f"cosine similarity: {cos:.4f}")
   ```

3. Compare with the similarity of the rank-1 video in the same anchor.
   A large gap (more than 0.05) usually indicates the encoder finds the
   queried video less directly relevant; a small gap means it's
   near-equally plausible and the ranking is fragile.

4. To see what the encoder is paying attention to, you can run the
   same query against a *sub-corpus* filtered by language or country
   combo:

   ```python
   hits = (tbl.search(q).metric("cosine")
              .where("country_combo = 'B'")
              .limit(10).to_pandas())
   print(hits[["YT_ID","TITLE","_distance"]])
   ```

## Add a new country combination

If you want to introduce a finer-grained country attribution (e.g.
distinguishing Russia-Russia-Russia from Russia-Belarus narratives),
this requires changes to the EDA pipeline that produces
`v2_feed_ready.csv.gz`.

1. Edit the country-flag derivation in `notebooks/EDA.ipynb`. The
   relevant cell builds `BY`, `UA`, `RU` boolean columns from text
   regexes, then composes `country_combo` as `"".join(["B" if BY else
   "", "U" if UA else "", "R" if RU else ""])`.

2. Add a new flag column. Example for a `LT` (Lithuania, where many
   Belarusian opposition outlets relocated):

   ```python
   df["LT"] = df["TEXT"].str.contains(r"\b(литв|Литв|Lithuania|Vilnius)\b",
                                       case=False, regex=True)
   ```

3. Decide whether the new flag is part of `country_combo` (changes the
   alphabet from `{B,U,R}` to `{B,U,R,L}`) or a separate `relocation`
   column. The first is more visible to downstream cluster-purity
   analysis; the second is less invasive.

4. Re-run the EDA notebook from the country-combo cell onward.

5. Re-run Stage A to refresh the LanceDB tables (the metadata columns
   are persisted with the vectors).

   ```bash
   python pipeline/stage_a_embed.py --model intfloat/multilingual-e5-small \
                                    --batch 32 --table videos
   python pipeline/stage_a_embed.py --model intfloat/multilingual-e5-large \
                                    --batch 8 --table videos_e5large
   ```

6. Re-run Stages B, C, D.

> **Why this is expensive.** Adding a new flag requires re-embedding
> the entire corpus, because metadata is stored alongside vectors in
> LanceDB. A future refactor could separate vectors from metadata
> into two parallel stores so that metadata edits don't trigger
> re-embedding.

## Update pinned dependencies

The `requirements.txt` uses lower-bound pinning (`pandas>=2.0`) with
the tested version recorded in comments. To refresh:

1. In a clean venv, install only `requirements.txt`:

   ```bash
   python3.11 -m venv /tmp/clean_v2
   /tmp/clean_v2/bin/pip install --upgrade pip
   /tmp/clean_v2/bin/pip install -r requirements.txt
   ```

2. Run the tests against the new versions:

   ```bash
   /tmp/clean_v2/bin/pytest tests/ -v
   ```

3. If tests pass, record the new "tested" versions in the comment
   column of `requirements.txt`:

   ```diff
   - sentence-transformers>=3.0 # tested 5.4.1
   + sentence-transformers>=3.0 # tested 5.5.0
   ```

4. Run a smoke test on the demo (see above) — unit tests do not
   exercise the encoder or LanceDB code paths, so a successful pytest
   alone is not sufficient.

5. Discard the throwaway venv: `rm -rf /tmp/clean_v2`.

> **What changes are risky.** `lancedb` API changes (`.metric()`,
> `.where()`, `.to_pandas()` keyword arguments) have historically
> required code edits. `sentence-transformers` API changes (e.g.
> `get_sentence_embedding_dimension` deprecation) have done the same.
> Lock-step upgrades only when you have time to investigate breakage.

## Debug a stage failure

When a stage script throws an error, the order of investigation:

1. **Check whether the input artefact exists and is non-empty.** Each
   stage expects specific inputs:

   | Stage | Expects |
   |---|---|
   | A | `outputs/v2_feed_ready.csv.gz` |
   | B | `outputs/v2_lancedb/<table>.lance/` |
   | C | `outputs/v2_lancedb/<table>.lance/` |
   | D | `outputs/retrieval/topk_per_anchor.csv` + `outputs/retrieval_e5large/topk_per_anchor.csv` |

   ```bash
   ls -la outputs/v2_feed_ready.csv.gz
   du -sh outputs/v2_lancedb/
   ```

2. **Check the input schema.** A common failure is that a column the
   stage expects is missing. For LanceDB tables:

   ```python
   import lancedb
   tbl = lancedb.connect("outputs/v2_lancedb").open_table("videos")
   print(tbl.schema)
   ```

3. **Run the stage with a smaller `--limit` (Stage A) or `--top-k`
   (Stage B).** A failure that happens on row 18,000 usually has a
   data-shape root cause; reproducing it on a smaller slice is
   faster.

4. **Check MPS availability if Stage A fails on `model.half()` or
   `model.encode`.** On Apple Silicon without MPS support:

   ```python
   import torch
   print("MPS available:", torch.backends.mps.is_available())
   print("torch:", torch.__version__)
   ```

   torch must be ≥ 2.4 for stable MPS support.

5. **Disk-space exhaustion.** Stage A writes ~345 MB; Stages B/C/D
   write under 10 MB total. If LanceDB write fails:

   ```bash
   df -h .
   ```

## Extend the corpus with new videos

When the underlying MariaDB is updated (e.g. metadata fetched for
videos that previously had only ID + tags):

1. Re-run the EDA notebook (`notebooks/EDA.ipynb`) to regenerate
   `outputs/v2_feed_ready.csv.gz`. The cell that computes
   `protest_anywhere`, `country_combo`, etc. should be deterministic
   given the same input data.

2. Re-run Stage A in full. Stage A overwrites the LanceDB table
   in place (`mode="overwrite"`):

   ```bash
   python pipeline/stage_a_embed.py --model intfloat/multilingual-e5-small \
                                    --batch 32 --table videos
   python pipeline/stage_a_embed.py --model intfloat/multilingual-e5-large \
                                    --batch 8 --table videos_e5large
   ```

3. Re-run Stages B, C, D.

4. Rebuild the demo dataset against the new source (see above).

> **For a partial update** (e.g., 1,000 new videos with metadata),
> in principle you could append rather than rebuild. The current
> `pipeline/stage_a_embed.py` overwrites; supporting append would
> need a `--append` flag, deduplication on `YT_ID`, and tests.
> Reserved for a future refactor; currently the rebuild path is the
> only supported one.

## Reproduce a published number

When a number appears in a paper, a talk, or in
`notebooks/pipeline.ipynb`, you should be able to reproduce it from
the code in this repo. The headline numbers and their source files:

| Number | Where | Source file |
|---|---|---|
| 21,710 videos | corpus size | `outputs/v2_feed_ready.csv.gz` row count |
| 9.4% protest-keyword rate | EDA finding | `outputs/v2_feed_ready.csv.gz` mean of `protest_anywhere` |
| 55% / 63% median newly-surfaced | Stage B claim | median of `small` / `large` columns in `outputs/retrieval_ensemble/comparison_summary.csv` |
| 17–56 / 100 overlap | Stage B complementarity | set intersections in `notebooks/pipeline.ipynb` cell `950add7e` |
| 11–18 percentage points gap | Hard anchors | difference of `large` − `small` for `RU-mobilisation-2022`, `RU-antiwar-2022`, `general-protest-action` in `comparison_summary.csv` |
| 61.2% / 62.0% cluster purity | Stage C | `cluster_purity()` function in `notebooks/pipeline.ipynb` cell `75ac843f`, applied to `outputs/polysemy{,_e5large}/cluster_assignments.csv` |
| 527 newly-surfaced (UNION) | Stage D headline | row count of `outputs/retrieval_ensemble/newly_surfaced.csv` |
| 315 / 329 single-encoder newly-surfaced | Stage D baseline | row count of `outputs/retrieval{,_e5large}/newly_surfaced.csv` |
| 8 polysemy clusters | Stage C structure | distinct values in `cluster` column of `outputs/polysemy{,_e5large}/cluster_assignments.csv` |

If a number cannot be reproduced from the current outputs, it is
either stale (run a fresh pipeline) or evidence of an undocumented
manual edit (investigate).
